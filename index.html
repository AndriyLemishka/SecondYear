📖 1. Що таке DNS і як воно працює в принципі?

DNS (Domain Name System) — це всесвітня розподілена база даних, що працює як «телефонна книга інтернету».

Чому без DNS не можна?

Мережеві маршрутизатори та операційні системи спілкуються виключно числовими IP-адресами (наприклад, 192.168.56.101). Людині ж зручно пам'ятати символьні слова (ns1.lan або google.com). DNS виконує функцію перекладача між людською та машинною мовами.

Як це працює по кроках:

1. Ти вводиш у браузері ns1.lan.
2. Комп'ютер звертається до DNS-сервера (порт 53) і питає: «Який IP у ns1.lan?».
3. Сервер знаходить запис у базі й повертає 192.168.56.101.
4. Комп'ютер підключається до цієї адреси.

📜 2. Історія: від HOSTS.TXT до RFC 1034/1035

У 1970-х роках у мережі ARPANET був лише один центральний файл HOSTS.TXT, який вів Стенфордський інститут (SRI-NIC). Коли в мережу додавали комп'ютер, адміністратор відправляв листа в Стенфорд, а всі інші вузли раз на тиждень завантажували оновлену копію файлу через FTP.

Чому стара система впала:

• Трафік: Стенфорд не витримував одночасних завантажень тисяч машин.
• Конфлікти імен: Якщо хтось зайняв ім'я mail, ніхто більше не міг його використати.
• Затримки: Зміни розходилися днями.

Рішення Пола Мокапетріса (1983 р.):

Стандарти RFC 1034 та RFC 1035 створили сучасний розподілений DNS: деревоподібну ієрархію, делегування зон та локальне кешування відповідей. Старий файл зберігся як локальний /etc/hosts.

🌲 3. Ієрархія доменного простору, FQDN та правило крапки

Дерево DNS перевернуте: корінь знаходиться вгорі, а конкретні комп'ютери — внизу.

                     [ . ]  (Корінь - Root Zone)
                   /   |                   .ua   .com   .org      (Домени верхнього рівня - TLD)
               /                    .lpnu      .google         (Домени другого рівня - SLD)
            /
          .cad                         (Субдомен третього рівня)
          /
        ns1                            (Хост / Комп'ютер)
        -------------------------------------------------------------
        Повне доменне ім'я (FQDN): ns1.cad.lpnu.ua. (із крапкою в кінці)
⚠️ Смертельна пастка для новачка: Крапка наприкінці FQDN (наприклад, ns1.lan.) повідомляє BIND, що це абсолютне ім'я. Якщо крапку пропустити (ns1.lan), BIND вирішить, що це відносне ім'я, і сам допише поточну зону. Вийде: ns1.lan.lan.!

🌍 4. 13 кореневих серверів та технологія Anycast

Вершину світового інтернету обслуговують 13 логічних кореневих адрес: від a.root-servers.net до m.root-servers.net.

Чому саме 13?

Це викликано лімітом стандартного UDP-пакета (512 байт), куди мали поміститися адреси всіх коренів разом із сигнатурами.

Anycast та вузол L-root в Україні

Сьогодні ці 13 адрес обслуговують понад 1500 фізичних серверів по всій планеті завдяки Anycast-маршрутизації. В Україні компанія «Хостмайстер» спільно з ICANN підтримує дзеркало l.root-servers.net (пінг менше 5 мс).

⚙️ 5. Що таке BIND 9 та демон named?

BIND 9 (Berkeley Internet Name Domain, version 9) — це відкритий комплекс програм для Linux/Unix, який перетворює машину на DNS-сервер. Створений в університеті Берклі, зараз розвивається консорціумом ISC.

named

Головний системний процес-демон (Name Daemon). Слухає порт 53 UDP/TCP.

named-checkconf

Перевіряє синтаксис файлів конфігурації. Порожній вивід = 0 помилок.

rndc

Remote Name Daemon Control — консоль оперативного керування через TCP 953.

// /etc/bind/named.conf.options у нашій лабі:
options {
    directory "/var/cache/bind";
    listen-on port 53 { 127.0.0.1; 192.168.56.101; };  // Наш Host-Only IP
    allow-query { localhost; 192.168.56.0/24; };       // Захист від DDoS Amplification
    forwarders { 8.8.8.8; 1.1.1.1; };                  // Пересилати зовнішні запити в інтернет
    dnssec-validation auto;
};

🔌 6. Порт 53: чому одночасно і UDP, і TCP?

Це улюблене питання викладачів. Ось чому використовуються обидва протоколи:

UDP порт 53 (99% повсякденної роботи)

Використовується для звичайних швидких запитів клієнтів (браузер, ping). Працює без затримок на 3-стороннє рукостискання.

TCP порт 53 (Коли підключається?)

1. Трансфер зон (Zone Transfer): передача всієї бази зони між серверами Master → Slave (потрібна 100% надійність).
2. Великі відповіді: якщо відповідь більша 512 байт, сервер ставить біт TC (Truncated), і клієнт перепідключається через TCP.

📑 7. Атлас ресурсних записів (Resource Records)

Формула будь-якого рядка в базі зони: [Ім'я] [TTL] [Клас IN] [Тип] [Дані/IP]

A та AAAA

client 14400 IN A 192.168.56.102
Пряме перетворення імені в IPv4 (32 біти) та IPv6 (128 бітів).

PTR (Покажчик)

101 IN PTR ns1.lan.
Зворотне перетворення IP в ім'я у спеціальній зоні in-addr.arpa.

CNAME (Псевдонім)

www IN CNAME ns1.lan.
Аліас на інше ім'я. Табу: якщо є CNAME, інших записів (A чи MX) бути не може!

MX (Пошта)

@ IN MX 10 mail.lan.
Поштовий шлюз домену із числовим пріоритетом (10). Менше число = вищий пріоритет.

👑 8. Запис SOA: розбір усіх 5 чисел («Паспорт зони»)

@   IN  SOA ns1.lan. root.ns1.lan. (
            2026111001 ; 1. Serial (Серійний номер версії: РРРРММДДNN)
            604800     ; 2. Refresh (Опитування вторинним сервером: 7 днів)
            86400      ; 3. Retry (Повтор при збої: 1 день)
            2419200    ; 4. Expire (Застарівання зони: 4 тижні)
            604800 )   ; 5. Negative Cache TTL (Кеш помилок NXDOMAIN: 7 днів)

Навіщо потрібен Serial Number?

Вторинні сервери порівнюють свій Serial із головним. Якщо число на головному більше — вони завантажують свіжу копію. Якщо відредагувати зону і забути збільшити Serial — вторинні сервери проігнорують оновлення!

Що таке Negative Cache TTL?

Скільки часу клієнтам дозволено пам'ятати, що запитаного домену НЕ існує (статус NXDOMAIN), щоб не засипати сервер повторними порожніми запитами.

🔄 9. Зворотний DNS (in-addr.arpa)

Чому IP-адреси в зворотній зоні записуються задом наперед?

Логіка розгортання:
У доменних іменах найширша частина стоїть праворуч (.ua), а конкретна машина — ліворуч (ns1).
В IP-адресах навпаки: мережа стоїть ліворуч (192.168.56), а номер хоста — праворуч (101).
Щоб деревоподібний механізм DNS міг знайти ім'я за IP, октети розгортають: 56.168.192.in-addr.arpa. Вузол 101 отримує ім'я 101.56.168.192.in-addr.arpa..

⏱️ 10. Час життя (TTL) та кешування

TTL (Time To Live) — це «термін придатності» запису в пам'яті клієнта чи провайдера.

3600 секунд

Рівно 1 година. Клієнт 60 хвилин бере адресу з кешу за 0 мс і не смикає сервер.

Чому не 1 секунда?

Сервер ляже від мільйонів однакових запитів користувачів кожні пів секунди.

Чому не 1 рік?

Якщо ви зміните IP сервера, користувачі ще цілий рік ходитимуть на мертву адресу.

🔀 11. Рекурсивні проти Ітеративних запитів

Рекурсивний запит (Клієнт → Сервер)

Клієнт каже: «Знайди мені IP сам, обійди хоч увесь світ і принеси готову відповідь». Прапорець RD = 1 (Recursion Desired).

Ітеративний запит (Сервер → Світ)

Сервер опитує корінь, TLD і SLD крок за кроком, отримуючи направлення (Referrals) на сервери нижчого рівня.

📋 12. Логування: де шукати query.log і що воно дає

Логування — це «чорна скринька» сервера для пошуку помилок та захисту від DDoS-атак.

Де логи в системі?

• За замовчуванням: sudo journalctl -u named -e
• У нашій лабі (виділений файл): /var/log/named/query.log
• Команда онлайн-перегляду: sudo tail -f /var/log/named/query.log

Розбір рядка з нашого логу:

10-Nov-2026 10:21:40 client @0x7f8 192.168.56.102#49210 (ns1.lan): query: ns1.lan IN A + (192.168.56.101)

Видно: час → хто питав (клієнт .102) → що шукав (ns1.lan) → тип (A) → куди надіслав (.101).

🛠️ 13. Діагностика: утиліти dig, nslookup, host

;; dig @192.168.56.101 ns1.lan
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 48312
;; flags: qr aa rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 1, ADDITIONAL: 1
;; ANSWER SECTION:
ns1.lan.    14400    IN    A    192.168.56.101

status: NOERROR

Запит успішний. Якщо NXDOMAIN — імені немає. Якщо SERVFAIL — збій конфігу.

Прапорець 'aa'

Authoritative Answer: відповідь надана первинним господарем зони, а не з кешу!

Query time: 0 msec

Запит виконано миттєво з локальної оперативної пам'яті сервера.

⚡ 14. Dynamic DNS (inadyn та cron)

Коли провайдер видає динамічну IP-адресу, клієнт inadyn кожні 5 хвилин перевіряє зовнішній IP. Якщо адреса змінилася — він відправляє HTTPS-запит сервісу DynDNS для оновлення запису.

Автозапуск закріплюють у crontab: @reboot /usr/sbin/inadyn.

⚠️ 16. «А що буде, якщо...?» (Головні пастки викладачів)

Забули крапку наприкінці FQDN?

BIND автоматично допише назву зони: замість ns1.lan. вийде ns1.lan.lan.. Клієнти не знайдуть сервер.

Змінили IP, але не збільшили Serial?

Вторинні (Slave) сервери не завантажать оновлення і продовжать віддавати стару неробочу адресу.

Повісили CNAME і A на одне ім'я?

Помилка синтаксису RFC 1034. CNAME забороняє існування будь-яких інших записів для цього імені.

Рестартнули без named-checkconf?

Якщо в конфігу є помилка — демон впаде у статус failed, і вся мережа залишиться без DNS.

🚨 17. Траблшутінг: розбір статусів помилок

SERVFAIL

Збій сервера. Помилка у файлі зони або відсутній A-запис для сервера, вказаного в NS (Glue record).

NXDOMAIN

Non-Existent Domain. Такого домену не існує. Перевірте крапки та правильність написання.

Port 53 in use

Порт зайняв systemd-resolved. Прив'язуйте BIND до конкретного IP 192.168.56.101 у named.conf.options.

📚 Повний глосарій термінів

FQDN (Fully Qualified Domain Name)

Повне абсолютне ім'я вузла, яке закінчується крапкою від кореня: ns1.lan..

BIND 9 (named)

Програмний комплекс DNS від ISC. Демон named слухає 53 порт UDP/TCP.

in-addr.arpa & PTR

Спеціальна зворотна зона, де октети IP розгорнуті навпаки для пошуку доменного імені.

CNAME (Canonical Name)

Псевдонім на інше ім'я. Забороняє наявність інших типів записів на цьому вузлі.

SRV (Service Location)

Службовий запис (порт, протокол), критично важливий для роботи Active Directory в Windows.

TTL (Time To Live)

Термін придатності відповіді в кеші (наприклад, 3600 секунд = 1 година).
